On an L4 GPU, the engine mattered less than the memory budget

46 benchmark runs of Qwen3-8B on vLLM and SGLang. The engines matched until KV-cache memory filled, and FP8 and prefix caching moved the numbers more than engine choice did. Here is what held up, and what didn’t.

The short version

  • The engines match until memory fills. Throughput is within about 4% up to 16 users. At 64, p95 time to first token (TTFT) is 388 ms on vLLM and 21.3 s on SGLang BF16, whose KV pool held 12,505 tokens against 27,024. Memory settings differed, so this is capacity, not an engine verdict.
  • FP8 weights are a speed lever. On vLLM, decode time per output token (TPOT) fell 42.8% (67.2 to 38.5 ms) and output rose 1.7×.
  • FP8 KV cache is a capacity lever. No effect up to 32 users (3% or less). At 64 it added 19% throughput on vLLM and 45% on SGLang.
  • RadixAttention pays off on shared prefixes. p95 TTFT fell 13.4× (17.3 s to 1.3 s) with an 81% shared system prompt. This is a best case.
  • FP8 did not measurably change GSM8K accuracy. BF16 scored 89.7% and the FP8 settings 89.3% to 90.5%, all inside the ±1.6 point interval.

How I measured

Every run used a single NVIDIA L4 GPU (24 GB, about 300 GB/s by spec) in a Lightning AI Studio, serving Qwen/Qwen3-8B in BF16 or the official FP8 checkpoint (block-wise W8A8). A custom closed-loop async load tester called /v1/chat/completions with max_tokens 256 and took token counts from the server's usage report. There were three workloads:

  • Static: 10 concurrent requests, 100 ShareGPT prompts (mean 229 tokens, median 42, p95 1,459).
  • Prefix cache: the same prompts behind a shared 986-token system prompt (mean 1,217 tokens).
  • Sweep: 1 to 128 concurrent requests in doubling steps, 60 seconds per level, BF16 and FP8 KV cache on both engines. Short prompts (mean 53 to 63 tokens), 256 output tokens each. The 128 level is provisional: my load tester capped in-flight requests near 100 (see open items).

Why the memory settings differ. The two flags budget different things. SGLang's --mem-fraction-static covers weights plus the KV pool, and activations sit outside it. vLLM's --gpu-memory-utilization covers the whole process.

I picked 0.78 for SGLang because its default fraction failed on this card: the KV pool shrank to 586 tokens and long prompts were rejected. Setting 0.78 leaves roughly 4–5 GB unallocated (the startup log reports available_gpu_mem of 4.05 GB), just under SGLang's 5 to 8 GB rule of thumb for activations, and I did not test higher values. In the BF16 sweep, SGLang peaked at about 19.1 GiB out of 22.5 GiB of VRAM, suggesting some unused headroom, though I did not test whether a higher static fraction would trigger activation OOMs during prefill bursts. Part of the gap to vLLM's 27,024-token pool is therefore a settings gap rather than an engine gap.

Noise floor

Two independent runs of the same vLLM configuration (a 2,048-token chunk is already the V1 default) agreed on throughput (0.57 req/s), TPOT (67.25 vs 67.39 ms) and p95 inter-token latency (ITL, 68.7 vs 69.1 ms), but TTFT moved about 30% (p50 342 vs 240 ms). So at 10 concurrent requests I trust throughput, TPOT and ITL, and treat TTFT differences under 30% as noise.

Finding 1: the engines match until KV-cache memory runs out

At these memory settings, SGLang's KV pool had room for about 40 requests and its latency collapsed at 64. vLLM's had room for about 86 and was still fast at 64.

The engines are level up to 8 concurrent requests (p95 TTFT 199 vs 193 ms), and throughput is within about 4% up to 16 (0.95 vs 0.91 req/s). They split at 16, where p95 TTFT is 217 ms on vLLM BF16 and 836 ms on SGLang BF16. At 64 it is 388 ms against 21.3 s.

The same data as a capacity answer: the highest tested concurrency under a p95 TTFT limit, and the throughput there.

Why capacity is the likely cause

A sweep request needs about 313 KV tokens at full length (a 57-token prompt plus up to 256 generated). Each engine's startup log gives its pool, so I can ask how many requests fit. Drag the slider to change the load.

The FP8 KV cache doubled SGLang's pool and grew vLLM's by 1.76×. For SGLang the effect is clear, and it is the stronger evidence: same engine and settings, only the KV dtype changed, and its 500 ms limit moved from 8 to 32 concurrent requests. The gap between engines is weaker evidence. vLLM's BF16 pool is 2.2× SGLang's, but part of that comes from my settings (SGLang's 0.78 budget leaves activations outside it, and it peaked near 19 GiB of 22.5 GiB), and CUDA graphs and chunk size also differ. Capacity is the likely cause, not proof of an engine gap.

The KV-cache arithmetic, and decode scaling

Qwen3-8B stores 36 layers × 8 KV heads × 128 head size × 2 (K and V) × 2 bytes = 147,456 bytes, about 147.5 KB, per token in BF16. The SGLang log confirms the pool: #tokens: 12505, K size: 0.86 GB, V size: 0.86 GB. FP8 halves the footprint to about 73.7 KB per token.

On decode: from 1 to 16 concurrent requests p95 TPOT rises only about 10% (60.1 to 65.7 ms on vLLM, 61.5 to 67.5 ms on SGLang), because at small batch sizes decode is limited by memory bandwidth and streaming about 15 GB of weights costs the same for 1 token or 16. From 16 to 128 it climbs to 80 to 88 ms as batches grow (the 128 level is provisional).

Finding 2: FP8 weights buy speed, FP8 KV cache buys capacity

FP8 weights made each token 43% faster. An FP8 KV cache made room for 1.8 to 2× more tokens.

The two settings address different bottlenecks.

  • Weights: on vLLM at 10 concurrent requests, the FP8 checkpoint cut TPOT from 67.25 to 38.47 ms (−42.8%) and raised output from 144.5 to 245.9 tok/s (1.70×).
  • KV cache: at 10 requests it changed neither TPOT nor throughput, because 10 requests hold only about 4,800 KV tokens. It pays off once BF16 runs out of pool: at 64 requests throughput rose 19% on vLLM (2.73 to 3.25 req/s) and 45% on SGLang (2.13 to 3.09). At the provisional 128 level, SGLang rose 62% and vLLM 2%.

A bandwidth check on the 1.7×

Each decode step reads the weights once: about 15 GB in BF16 and 8.2 GB in FP8 (estimates from parameter counts). At the L4's 300 GB/s spec that gives a TPOT floor of about 50 ms and 27 ms, and vLLM sustains roughly 70 to 75% of that bandwidth in both precisions. Halving the bytes gave 1.70× instead of 2×, most likely because fixed per-step costs (kernel launches, attention, activation scaling) are a larger share of a 38.5 ms step.

The SGLang W8A8 run is the exception. TPOT rose to 72.3 ms and GPU utilization fell from 98.4% to 53.5%. Two causes are plausible, and I have tested neither: CUDA graphs were off, so CPU-side launch overhead may dominate, and SGLang logged a warning that no tuned block-FP8 kernel config exists for this GPU. Until I rerun with CUDA graphs enabled, treat this as an untuned configuration, not SGLang's FP8 ceiling.

Finding 3: RadixAttention pays off when prompts share a prefix

With a shared prefix, caching it cut p95 first-token latency 13.4×, on this best-case workload.

To test a RAG-style workload, I put a 986-token system prompt in front of the same 100 user turns. By the server's usage reports the shared part is 81.04% of the mean prompt (95.8% at the median), and the user turns overlap only 0.3%, so nearly all cache hits come from the shared template.

Two effects are mixed here, and I did not separate them. With the cache on, about 81% of each prompt is not recomputed, which cuts prefill work for every request. And the shared prefix is stored once, which relieves KV-pool pressure: ten requests of about 1,217 prompt tokens plus up to 256 output tokens need about 14,730 KV tokens, more than SGLang's 12,505-token pool, so some wait for admission. Storing it once saves about 8,874 tokens. Pool pressure most likely drives the 17.3 s tail, but this run cannot prove it.

This is a best case. A RAG pipeline or agent with a fixed template looks like this run. A chat service where every prompt is unique would see close to no benefit. Each setting is a single run of 100 requests.

Finding 4: structured decoding taxes every token, and small prefill chunks hurt the tail

Forcing JSON slowed every token by about 22%, and a 512-token chunk made the worst pauses about 1.8× longer in this run.

Structured output

Enforcing a JSON schema on SGLang (xgrammar backend) raised mean TPOT 21.6% (69.9 to 85.0 ms), p95 ITL 1.97× and p99 ITL 3.75× (134.0 to 502.7 ms), and cut raw generation speed 24.8% (137.9 to 103.6 tok/s). Request throughput still rose 4.15× and median end-to-end latency fell 5.3×, but that is an output-length effect: unconstrained responses averaged about 251 tokens and JSON-constrained ones about 45.

Prefill chunk size on vLLM: 512 vs 2,048

Throughput (0.56 vs 0.57 req/s), TTFT and p95 ITL (68.6 vs 69.1 ms) are the same. p99 ITL is 130.9 ms at 512 against 74.5 ms at 2,048 and 71.1 ms in the baseline replicate, so the 512 tail is about 1.8× worse. A likely reason is that long prompts split across 3 to 5 scheduler steps, so more decode steps share a batch with prefill work; I did not test that. Each size is a single run, so this shows 512 was worse here, not that 2,048 is optimal.

Finding 5: FP8 did not measurably change accuracy

Across 1,319 GSM8K questions, dynamic FP8 weights and an FP8 KV cache did not move accuracy outside the margin of error.

I ran all 1,319 GSM8K test questions (5-shot, greedy) through lm-evaluation-harness against vLLM in each configuration. The FP8 weight runs used vLLM's online dynamic FP8 (--quantization fp8 on the BF16 model), not the pre-quantized block-wise Qwen3-8B-FP8 checkpoint behind the speed numbers. Scores use the flexible-extract filter; strict-match tells the same story.

Every gap is smaller than the interval. The paired test, which asks whether the questions flipped one way more often than chance allows, gave p = 0.30 at the lowest (by convention, p below 0.05 counts as significant). So the +0.8 points for the combined setting is noise, not an improvement. What is visible is churn: even FP8 KV alone changed the answer on 58 of 1,319 questions (4.4%), 29 each way.

What this does not show. It is one benchmark and one run with greedy decoding. GSM8K is short-context math, so it says little about long-context retrieval, code or multilingual quality, where KV-cache precision may matter more. Read it as “no measurable drop on GSM8K”, not “no quality loss”.

What did not hold up, and what is still open

  • The 128-user level is provisional. My load tester capped in-flight requests at 100 (aiohttp's default connection limit, confirmed in the server logs), so that level measured about 100 concurrent requests, and time spent waiting for a free connection may have been counted as TTFT. I will rerun it with the limit raised. Until then the conclusions rest on 64 concurrent requests and below, and I do not know where vLLM's wall is: its BF16 pool should hold about 86 requests and its FP8 KV pool about 150.
  • SGLang's memory fraction and CUDA graphs differ from vLLM's. SGLang ran at --mem-fraction-static 0.78 with CUDA graphs disabled in every run. I will rerun it with a higher fraction and with graphs enabled. Either may change its pool size, decode speed and W8A8 result.
  • An unresolved 11.9-second pause in the SGLang W8A8 run. p95 and p99 TTFT (11,921.11 and 11,921.72 ms) differ by 0.61 ms, so at least 5 or 6 requests got their first token at the same instant: one server-wide stall, not queuing. The log shows a Triton kernel compiling after serving started, but I have not tied it to the pause. The next run did not show it, and one clean run does not show that the KV flag fixed anything.
  • The baseline p50 TTFT gap is real but unexplained. vLLM's p50 is 38.6% lower (342 vs 557 ms), beyond the noise band, while p95, TPOT and throughput are level. One untested candidate is that the median 42-token prompt fits vLLM's CUDA graph capture range while SGLang ran without graphs. Launch flags differ in other ways too, so I make no causal claim.
  • Small TTFT gains at 10 concurrent requests are noise. Two identical vLLM runs differed by about 30%, so a result like the 22.5% p95 drop from adding FP8 KV (1,385 to 1,073 ms) cannot be separated from arrival-order variance. I do not claim it.
  • The FP8 checkpoint's accuracy is not measured. The GSM8K runs used vLLM's dynamic FP8 on the BF16 model, not the Qwen3-8B-FP8 checkpoint behind the speed numbers. Running the checkpoint through the same test is on my list.
  • Scope. One GPU (L4), one dense 8B model, GSM8K as the only quality check, and one run per setting except where noted. Higher-bandwidth GPUs or mixture-of-experts models would shift the balance between compute and bandwidth limits.

Problems along the way

  • Three RunPod pods failed CUDA initialization, so the final runs are on a Lightning AI Studio L4.
  • SGLang's FlashInfer CUDA graph kernels failed to compile on RunPod, which is why graphs are off.
  • SGLang's default memory fraction left a 586-token KV pool on the L4, which is why I set 0.78.

Reproduce it

The raw JSON for every run, the server logs, the manifest and the plotting scripts are in the GitHub repository. python3 analysis/analyze.py regenerates summary.csv and every figure from the raw JSON.

Commands for the accuracy check and the bandwidth chart 
# accuracy: start the vLLM server in one configuration, then
lm_eval --model local-completions \
  --model_args model=Qwen/Qwen3-8B,base_url=http://localhost:8000/v1/completions,tokenizer=Qwen/Qwen3-8B,num_concurrent=16,max_retries=3 \
  --tasks gsm8k --num_fewshot 5 \
  --gen_kwargs temperature=0,max_gen_toks=512 \
  --seed 0 --log_samples --output_path results/acc_bf16

# FP8 weights run: vllm serve Qwen/Qwen3-8B --quantization fp8   (FP8 KV adds --kv-cache-dtype fp8)

# bandwidth chart with your own numbers instead of the spec and the estimates
BW_GBS=<measured GB/s> WEIGHTS_BF16_GB=<n> WEIGHTS_W8A8_GB=<n> python3 analysis/analyze.py
